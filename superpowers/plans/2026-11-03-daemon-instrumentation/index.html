    데몬 instrumentation 이동 — 구현 계획¶

    For agentic workers: REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (- [ ]) syntax for tracking.

    Goal: 데몬을 app_process에서 설치된 APK의 instrumentation 프로세스(am instrument -w)로 옮긴다. UiAutomation은 공식 API로 얻고, monkey는 정식으로 켠다. 모든 verb의 동작은 유지한다.

    Architecture: - 같은 APK(dev.mobileax.daemon)에 androidx.test.runner.MonitoringInstrumentation(AndroidJUnitRunner의 부모) 서브클래스를 둔다. AMS가 fork한 프로세스의 main looper 위에서 지금의 서버·코루틴 구조를 그대로 돌린다. - instrumentation, context, 인자는 InstrumentationRegistry로 얻는다. UiAutomation은 UiDevice와 같은 인스턴스를 쓴다. 데몬 경로 중 androidx.test로 바꿔도 결과와 성능이 같은 곳은 바꾼다(spec 5.1). - shell 권한이 필요한 일은 두 갈래로 처리한다. 권한 검사는 adoptShellPermissionIdentity()로 통과하고, shell uid 자체가 필요한 일은 executeShellCommand*(shell uid로 실행)로 넘긴다. - 호스트 쪽은 기동과 정리 경로만 바뀐다. 기존 jar push + app_process 대신 APK 설치 + am instrument를 쓴다.

    Tech Stack: Kotlin(데몬, AGP, kotlinx-coroutines, androidx.test runner/monitor/uiautomator), Rust std-only(CLI), adb, GitHub Actions

    Spec: docs/superpowers/specs/2026-11-03-daemon-instrumentation-design.md

    Global Constraints¶

    • minSdk = 29(최종 검토 뒤 사용자 결정으로 31에서 낮춤, spec 3절), compileSdk = 36, targetSdk = 36.
    • 패키지 dev.mobileax.daemon, 소켓 이름 mobaxd_<port>(abstract)는 그대로 둔다. 와이어 프로토콜(docs/wire.md)은 바뀌지 않는다.
    • 릴리즈 APK도 signingConfigs.debug로 서명한다. 키 파일과 CI 시크릿은 쓰지 않는다.
    • app_process 기동 경로는 남기지 않는다(전체 이동).
    • 데몬은 기기당 하나다. 다른 --port로 use하면 오류를 낸다. 메시지에는 mobax drop 후 다시 하라는 안내를 넣는다.
    • CLI는 third-party 의존성 없이 std만 쓴다(mobax-cli/Cargo.toml 주석).
    • 데몬 의존성은 androidx.test:runner, androidx.test:monitor, androidx.test.uiautomator:uiautomator를 추가한다. 구현 시점의 최신 안정 버전을 정확한 버전으로 고정한다.
    • UiAutomation 연결 플래그는 한 곳의 상수 UA_FLAGS = UiAutomation.FLAG_DONT_SUPPRESS_ACCESSIBILITY_SERVICES로 두고, Configurator.getInstance().uiAutomationFlags에도 같은 값을 넣는다.
    • androidx.test로 바꾼 경로가 아래 기준선을 해치거나 결과를 바꾸면 그 경로는 지금 코드를 유지하고, 이유를 코드 주석에 한 줄 남긴다(spec 5.1).
    • Task 1의 확인 1(소켓 도달)이나 확인 2(monkey 켜기·끄기)가 실패하면 프로젝트를 중단한다. 대체 방식(TCP + adb forward, setActivityController)으로 가지 않는다.
    • 성능 기준선(SDK 36 에뮬레이터 Medium_Phone)에서 잡음을 넘는 회귀가 없어야 한다.
    • 유휴 ui 약 265ms
    • tap→하위 화면 중앙값 약 976ms
    • Recents 키 응답 약 627ms
    • 드래그 약 126ms
    • 첫 dump_active 약 158ms
    • 기기 작업은 저장소 규칙을 따른다.
    • 에뮬레이터는 android emulator start Medium_Phone으로 띄운다. 새 AVD는 만들지 않는다.
    • 프로세스는 이 저장소 target\ 바이너리만 PID로 종료한다. 이미지 이름으로 taskkill하지 않는다.

    Review Focus¶

    1. am instrument 프로세스가 죽은 경우 (USB 재연결, adb kill-server 등): 데몬도 죽는다. 다음 명령은 "no daemon … start it with mobax use"로 실패해야 하고, use는 재설치 없이 다시 띄워야 한다. → Task 7 Step 7
    2. 기기에 다른 서명으로 설치돼 있는 경우 (다른 PC나 CI에서 만든 빌드): use가 자동으로 지우고 다시 설치해야 한다. → Task 7 Step 1(파싱 테스트), Step 7(기기 확인)
    3. 읽을 수 없는 파일을 cp로 받거나 쓸 수 없는 경로로 보내는 경우: 오류로 끝나야 한다. "pulled 0 bytes" 같은 성공으로 끝나면 안 된다. → Task 4 Step 4
    4. 데몬이 비정상 종료한 경우 (크래시, am force-stop): 기기가 monkey 상태로 남으면 안 된다. → Task 1 확인 2, Task 8 Step 3
    5. 다른 UiAutomation이 이미 연결돼 있는 경우 (사용자의 UiAutomator 테스트 실행 중): use가 6초 타임아웃으로 멈추지 말고 원인을 담은 오류를 내야 한다. → Task 2 Step 5

    Task 1: 위험 확인 스파이크 (버리는 코드)¶

    이 작업의 코드는 커밋하지 않는다. 결과만 계획 문서 끝의 "스파이크 결과" 절에 적고 커밋한다.

    Interfaces: - Produces: 확인 1~5의 성공·실패 기록. 실패한 항목이 있으면 이후 Task의 범위가 바뀐다.

    • [ ] Step 1: 스파이크 instrumentation 작성

    SpikeInstrumentation : androidx.test.runner.MonitoringInstrumentation이 하는 일. 스파이크 동안에만 build.gradle.kts에 Task 2의 androidx.test 의존성을 임시로 추가한다. - onCreate(main 스레드)에서 LocalServerSocket("mobaxd_spike")를 연다. - 별도 스레드에서 accept하고, 길이 접두(uint32 BE) 프레임 ping에 pong으로 답한다. 와이어 형식과 같다. - start()는 부르지 않는다. - 아래 결과를 sendStatus(0, Bundle().apply { putString("spike", line) })로 내보낸다. - ActivityManager.getService().setUserIsMonkey(true)(리플렉션) 결과 - ActivityManager.isUserAMonkey() 값 - Work 스레드에서 getUiAutomation()으로 연결한 결과 - 3-arg injectInputEvent(ev, false, false) 리플렉션 결과 - adoptShellPermissionIdentity() 아래에서 확인 4의 각 항목 결과 - 확인 6: Configurator.getInstance().uiAutomationFlags = UA_FLAGS 후 UiDevice.getInstance(this)를 만들고, 그 uiAutomation이 getUiAutomation(UA_FLAGS)와 같은 인스턴스(===)인지 - 확인 7: super.onCreate(arguments)만 부르고 start()는 부르지 않은 상태에서, 5분 동안 프로세스와 am instrument -w가 살아 있는지. MonitoringInstrumentation이 스스로 finish()하지 않는지를 본다.

    manifest에는 다음을 추가한다. 

    <instrumentation android:name="dev.mobileax.daemon.SpikeInstrumentation" android:targetPackage="dev.mobileax.daemon" />

    스파이크 결과 (Task 1, 2026-11-03, 에뮬레이터 Medium_Phone SDK 36)¶

    androidx.test 버전: runner 1.7.0, monitor 1.8.0, uiautomator 2.4.0 (구현 시점 최신 안정판). 스파이크 프로세스는 uid 10217(앱)로 돌았다.

    확인 결과
    1. 앱 uid의 abstract 소켓 도달 (중단 조건) 통과. adb forward tcp:… localabstract:mobaxd_spike와 adb server 경로(host:transport: + localabstract:) 모두 pong
    2. monkey 켜기·끄기 (중단 조건) 통과. setRunAsMonkey(true) → isUserAMonkey=true. am force-stop 후 재실행 시 false. 일부러 크래시(Process crashed.)시킨 뒤 재실행도 false. 둘 다 am instrument 프로세스가 같이 끝났고 남은 프로세스 없음
    3. 3-arg injectInputEvent(ev, false, false) 통과. down/up 모두 true
    4. adopt 아래 권한 작업 통과. AUTO_MIRROR 가상 디스플레이 생성, Settings.Global.putInt, content://sms 쿼리, PackageInstaller 세션 생성·폐기, ClipboardManager 쓰기·읽기
    5. shell 실행의 stderr·종료 코드 통과(방식 변경). executeShellCommand*는 명령을 공백으로만 자르고 따옴표를 처리하지 않는다(sh -c '…' → no closing quote). executeShellCommandRwe("sh")를 띄우고 스크립트를 stdin으로 넣으면 uid 2000(shell), 따옴표 정상, __MOBAX_EXIT:1/:0 수신
    클립보드 통과. adopt 아래 ClipboardManager로 읽기·쓰기 됨. cmd clipboard도 존재(cmd -l)
    6. UiDevice와 같은 UiAutomation 통과. Configurator.uiAutomationFlags = 1 후 UiDevice.getInstance()를 써도 getUiAutomation(1)이 같은 인스턴스(same=true)
    7. start() 없이 5분 생존 통과. 300초 후에도 프로세스와 am instrument가 살아 있고 소켓이 pong

    androidx.test 대체 결과 (Task 5b, uiautomator 2.4.0 소스와 에뮬레이터 SDK 36 기준)¶

    후보 판정 근거
    wm_rotation 바꿈, 단 UiDevice 대신 공개 API UiAutomation.setRotation UiDevice에는 180° 설정이 없다(setOrientationLeft/Right/Natural/Portrait/Landscape뿐). IWindowManager.freezeRotation 리플렉션을 공개 API로 바꿨다. 0~3 모두 user_rotation이 같은 값이 되고 accelerometer_rotation=0, 이전 경로와 같다. 범위 밖 값은 ERR:bad-rotation:N(이전에도 ERR)
    wait_for_idle 유지 UiDevice.waitForIdle은 조용한 시간이 500ms로 고정(QUIET_TIME_TO_BE_CONSIDERED_IDLE_STATE)이라 idle_ms를 못 받고, 응답의 idle=(조용했던 시간)도 줄 수 없다
    wait_for_text 유지 Until/WaitMixin은 100ms 폴링이다(DEFAULT_POLL_INTERVAL). 지금은 접근성 이벤트마다 다시 확인한다. scope=active와 match= 모드도 By로 같게 표현되지 않는다
    wait_for_activity 유지 getCurrentPackageName은 패키지만 준다. 지금은 정확한 컴포넌트 또는 같은 패키지를 확인한다
    info의 화면 크기 유지 info는 캡처·스트림이 쓰는 원본 크기(shot.sourceSize)를 돌려준다. 다른 출처(getDisplaySize)로 바꾸면 캡처와 어긋날 수 있다. 세로 고정 앱만 있어 가로 상태 비교는 못 했다
    키 이름 → 키 코드 유지 pressKeyCode는 동기 주입이라 애니메이션을 기다린다(지난 측정: Recents 5492ms 대 627ms)
    tap, swipe, 드래그 유지 같은 이유(click/swipe/drag는 동기 주입)
    dump 유지 dumpWindowHierarchy는 XML이라 호스트 파서와 맞지 않는다
